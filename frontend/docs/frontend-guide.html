How we build the frontend

One application, four areas of work, one visual language. This is the reference for adding your part: where your code goes, what it may assume, and what it must not change.

Branches

feature/frontend-layout is the develop branch of the frontend. It holds the shell, the theme, the routing and the shared pieces. You branch from it, build your screen, and merge back into it. It goes to develop once, as one coherent application, rather than four times as four different-looking halves. 

git checkout feature/frontend-layout
git pull
git checkout -b feature/frontend-<your-area>
# build, commit, then open a pull request into feature/frontend-layout
Rebase onto the layout branch before you open the PR. The shared pieces move while you work. A rebase turns that into your problem for ten minutes instead of the reviewer's problem for an hour.
Do not merge your branch into develop. One route added directly to develop is one route the rest of the application has never rendered beside. Everything goes through the layout branch.

The shape of the application

A fixed rail of pages on the left, a thin bar across the top saying which repository and release are being looked at, and one work surface. Nothing else moves.

The sidebar names places, not steps

The sidebar is where a person can go. It is not the process. A person comes back to look at a result far more often than they run the analysis, and a sidebar full of steps makes every screen feel like part of a wizard they have to finish.

The process lives on the pipeline screen, drawn as a pipeline, which is the one place in the application where order means something and the one place where motion is allowed.

Nothing on screen says which team built it

No screen, label, tooltip or error message names a research component, a module or a person. A reader cares what the thing is. Use the product's words:

What is reserved for you

Three screens exist as placeholders. Each one already has its route, its name, its position in the sidebar and a page saying what belongs there and which endpoints it reads. You replace the placeholder; you do not invent the name or the path.

Open the reserved page in the running application before you start. It lists what that screen is expected to show and the endpoints it reads, so the first question is already answered.

Your folder is yours. Nothing outside features/<yours>/ imports from inside it, except the one line in router.tsx that mounts it. That is what makes a redesign of your screen a change to one directory, and what lets two people work in the same week without a conflict.

Adding your page

  1. Create the folder src/features/<area>/ with a page component, and any pieces only that page uses.
  2. Add the calls you need A new module under src/lib/api/, one line in src/lib/api/index.ts. Types mirror the backend's response schema field for field.
  3. Mount it In src/router.tsx, replace the placeholder element with your page. The path and the label do not change.
  4. Flip the state In src/layouts/navigation.ts, change your page's state from reserved to ready. The sidebar stops saying "soon" and the pipeline stops saying the screen is not built.
  5. Delete the placeholder Remove your entry from src/features/reserved/reservedPages.tsx.

Calling the backend

One place knows a URL. Everything else calls a named function and gets a typed shape back. A route that moves is then a change in one file rather than a search across the application. 

// src/lib/api/drift.ts
import { get, type RequestOptions } from './client'

export interface DegradationEvent {
  element_id: string
  anti_pattern_type: string
  lifecycle: string
}

export function listDegradation(systemId: string, options?: RequestOptions) {
  return get<DegradationEvent[]>(`/degradation/${encodeURIComponent(systemId)}`, options)
}

Then, in your page:

const { data, isLoading, error, reload } = useRequest(
  (options) => listDegradation(systemId, options),
  [systemId],
)

useRequest handles the four states every screen needs — the data, whether it is still coming, what went wrong, and a way to ask again — and aborts the request when the component unmounts. Write those four by hand four times and you get four different answers to "what happens when it fails".

Show the backend's own words. It says which branch does not exist and which release was never ingested. ApiError.message already carries that; replacing it with "Something went wrong" throws away the only useful part.

The design system

Every colour, radius and font is a token in src/styles/tokens.css, used through Tailwind utilities. Re-skinning the application is editing that one file — which only works if the rule is absolute.

fieldthe page
panela card
raisedhover, active
inkprimary text
ink-3secondary text
okhealthy, confirmed
warnneeds a person
badfailed, contradicted
aia model was involved

The four signals mean one thing each. Purple means a language model touched it, everywhere, and nothing else is purple. Green is healthy or confirmed, amber needs a person, red failed. Do not reach for one because it looks right in a layout.

Use the primitives

src/components/ui/ has Card, Button, Pill, Field, Tabs, Stat, StatRow, EmptyState, ErrorState, Spinner and PageHeading. Every screen opens with a PageHeading and is built from Cards, so the pages look like one application rather than four.

Give it room

Card padding is p-7, the gap between sections is gap-10, and the content column is capped so running text never crosses a screen. Dense is not the same as informative: a figure with space around it gets read, and one without it gets skimmed past.

Charts and diagrams

  • Draw it yourself in SVG. No chart library and no graph library — see rule 6.
  • Positions must be a function, never a simulation. A force-directed layout settles differently every load, so one release looks like two systems and two releases look unrelated. features/architecture/layout.ts is the layered layout to copy.
  • Colour is never the only carrier. Every state also has a line style, a glyph or a word. A washed-out projector and a printed appendix both have to work.
  • Do not recompute what the backend counted. A total worked out in the browser is a second implementation of it, and the two disagree on exactly the release somebody is looking at.

The rules

1 · Feature-sliced

Everything for one area lives in one folder. Nothing outside imports from inside it, except the router line that mounts it.

2 · One theme file

No hard-coded colour anywhere else. One bg-[#1e293b] in one component breaks the promise that re-skinning is one file, because the next person has to grep instead of edit.

3 · Components take props; hooks fetch

A component that fetches cannot be rendered on its own, which makes it unreviewable without a running backend. One hook per screen does the loading.

4 · Render lists from data, not from a list of components

If the backend returns an array of stages, map over it. Nine named components for nine stages means the backend cannot add a tenth without a frontend change.

5 · Every screen has an empty state and an error state

And the empty state says why it is empty. "No findings" and "nothing has been run yet" are different facts, and a screen that renders both as a blank panel is lying about one of them.

6 · No new dependencies without asking

Every package changes package-lock.json, which everyone resolves. React, React Router and Tailwind are what we have. A chart for twelve nodes is not worth a lockfile conflict for four people.

7 · Motion only where it means something

The pipeline flows because the flow is the explanation. Nothing else animates. Honour prefers-reduced-motion: the states still have to arrive without the travel between them.

Before you open a pull request

  • npm run build passes — it type-checks as well as builds.
  • npm run lint is clean. Not "only warnings": clean.
  • Your screen renders with the backend stopped, and says something useful.
  • Your screen renders with nothing ingested, and says what to do about it.
  • No colour, radius or font outside the tokens.
  • No component name, label or message mentions a research component or a person.
  • It is readable at phone width, and from the back of a room at presentation zoom.
  • You rebased onto feature/frontend-layout.
Run it. npm install once, then npm run dev with the backend on :8000. Set VITE_API_BASE_URL in .env.local if your backend is somewhere else.
